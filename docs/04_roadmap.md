# 04. Phase 2 以降の改善候補

Phase 1 は「動くこと優先」で作ってあります。ここは**まだ実装していない**改善案です。
優先度は、Phase 1 を実際に回してみてから決めるのが妥当だと考えています。

## 1. 人物保持の強化

| 案 | 内容 | 追加依存 |
|---|---|---|
| **Profile の永続化** | Character Profile をファイルに保存／読み込みするノードを入れ、クリップ間で確実に同一のテキストを使う | 文字列 I/O ノード（`comfyui-easy-use` などに候補あり） |
| **Subject 定義ブロックの固定** | `subject_definitions` の `<Subject 1>` 行だけを固定テキストにして、VLM には残りだけ書かせる | なし |
| **顔クロップの自動生成** | 参照画像から顔だけを自動で切り出し、`ref_image_4` に高解像度で追加投入する | `comfyui_controlnet_aux`（導入済）または BiRefNet（導入済） |
| **参照サイズの自動配分** | 参照枚数に応じてトークン予算を自動配分し、主役だけ厚くする | `MathExpression`（導入済）で実装可 |
| **Krea2 での事前キャラ固定** | Krea2 + `krea2_identity_edit_v1_1_r128`（導入済）で参照シート自体を作り込んでから H3 に渡す | すでに全部導入済み |

> LTX の FaceID 的な「埋め込みで顔を縛る」機構は H3 側に該当ノードがないため、
> **参照画像の質と Profile テキストの精度**で代替するのが現実的だと考えています。

## 2. 続き生成の安定化

| 案 | 内容 |
|---|---|
| **同一グラフ内 2連鎖** | S3 コアを2セット並べ、1本目の出力を2本目の `ref_video_0` に直結。1実行で最大30秒。VRAM とグラフの複雑さは増える |
| **tail 長の自動調整** | 直前クリップの動きの激しさ（フレーム差分）で tail を 39〜90 の間で自動選択 |
| **ドリフト検出** | クリップごとに顔領域を切り出して比較し、閾値を超えたら警告。`ImageConcatMulti` + 目視でも可 |
| **カット割りモードの明示化** | Tail Relay を切って参照画像だけで新規生成する「意図的なカット」モードをプリセット化 |
| **クリップ連結の自動化** | `LoadVideo` ×N → `BatchImagesNode` + `AudioConcat` 連鎖で最終尺を一括生成。ノードはすべて導入済み |

> ショート動画はカット割りが多いほうがテンポが出るため、
> 実運用では「カット割り主体 + 要所だけ Tail Relay」が現実的だと考えています。

## 4. 2Pass 補正の検討

LTX の2パス思想（低解像度で構図確定 → 高解像度で描き直し）を H3 に持ち込む案。

| 案 | 内容 | 懸念 |
|---|---|---|
| **解像度2段運用（実質1.5パス）** | 576×1024 で seed 固定して構図確定 → 768×1344 で本番。**Phase 1 でも手動で可能** | なし。今すぐ運用でできる |
| **H3 出力を再度 H3 に通す** | 1パス目の出力を `ref_video_0` に入れて低 denoise で回す | H3 の `SamplerCustomAdvanced` は denoise を持つが、参照動画経由の再生成は挙動未知 |
| **SeedVR2 での後段補正** | 導入済みの `seedvr2_ema_7b_fp16`（15.35GB）で映像を作り直す | VRAM 重い。12GB では要検証 |
| **LTX ic-lora-detailer** | 記事版と同じ構成 | 追加 30GB DL。費用対効果が低いと判断して Phase 1 では不採用 |

> まずは **解像度2段運用**を試すのが一番安上がりだと思います。

## 7. デュアル GPU

> ⚠️ **`ComfyUI-MultiGPU` は現時点で有効化しないでください。**
> Windows で `libcudart.so` を読みに行って `FileNotFoundError` になる既知バグが
> 導入済み v2.6.4 にも上流 `main` にも残っています（Issue #187 / #210 ともに Open）。
> しかも起動時ではなく**GPU をまたいだ瞬間**に落ちるため発見が遅れます。
> 詳細と再現ログは [03_missing.md](03_missing.md) B-2 を参照してください。
>
> また 4070 Ti と 3060 の間に NVLink はないため、バグを直しても P2P は成立せず
> 「CPU 経由のステージング」動作になります。速度面の期待値は高くありません。

修正が入った場合の割り当て案（**未検証の構想**）：

| 割り当て | 理由 |
|---|---|
| H3 DiT → GPU0 (4070 Ti) 専有 | 毎ステップ動くので最速の GPU を独占させる |
| テキストエンコーダ → GPU1 (3060) + CPU オフロード | 1回しか使わない。64GB RAM が効く |
| VAE → GPU1 | デコードは DiT と同時に走らない |

### ★重要な訂正：ComfyUI は GPU を分散していない（llama.cpp が現在デバイスを動かしていた）

**以前ここに「ComfyUI 本体が自動で2枚目の GPU に分散している」と書きましたが、誤りでした。訂正します。**

#### 確定した事実（コード＋対照実験）

ComfyUI の `comfy/model_management.py`:

```python
def get_torch_device():
    ...
    return torch.device(torch.cuda.current_device())   # ← 単一デバイス

def vae_device():
    if args.cpu_vae: return torch.device("cpu")
    return get_torch_device()                          # ← VAE も同じデバイス
```

**ComfyUI は「現在の CUDA デバイス」1枚しか使いません。** 分散機構はありません。

#### 対照実験

同じビルド・同じ起動引数で、グラフの内容だけ変えて比較：

| グラフ | ログの `VAE load device` |
|---|---|
| Test 3（Gemma VLM を含む） | **`cuda:1`** |
| VAE のみ（VLM なし） | **`cuda:0`** |

起動時ログは両方とも `Device: cuda:0 NVIDIA GeForce RTX 4070 Ti`（＝起動時点では cuda:0）。

**結論：llama.cpp が GPU レイヤーを分割して読み込む際に
プロセスの `torch.cuda.current_device()` を 1 に変更し、
その後に読み込まれた ComfyUI のモデルがすべて cuda:1 を継承していました。**

つまり **Test 3 の DiT とサンプリングは RTX 3060 で走っていました。**
55.5 秒/step という数字はそのためです。

> DiT の `load device` を明示するログ行は存在せず（VAE と CLIP のみ出力される）、
> 私は VRAM の増減から推測して「DiT は cuda:1」と書いていました。
> 推測を事実として報告したのは誤りでした。

#### 対処

`--cuda-device 0` を付けて起動すると `CUDA_VISIBLE_DEVICES=0` が設定され、
プロセスからは 4070 Ti しか見えなくなります。

```
[INFO] Set cuda device to: 0
[INFO] Device: cuda:0 NVIDIA GeForce RTX 4070 Ti : cudaMallocAsync
```

デバイス1が存在しないため llama.cpp も移動できず、**DiT は確実に 4070 Ti に載ります。**

#### 「DiT=4070Ti / VAE=3060」の理想構成について

`vae_device()` が `get_torch_device()` のエイリアスである以上、
**素の ComfyUI ではモデルごとにデバイスを振り分けることはできません。**
それを可能にするのが ComfyUI-MultiGPU ですが、
[03_missing.md](03_missing.md) B-2 の Windows バグのため無効のままにしています。

したがって現構成で到達可能な最善は：

| デバイス | 担当 |
|---|---|
| **RTX 4070 Ti (cuda:0)** | H3 DiT / サンプリング / VAE（`--cuda-device 0`） |
| RTX 3060 | **未使用**（ComfyUI からは見えない） |
| CPU | テキストエンコーダ（`CLIPLoader.device=cpu`） |

3060 を遊ばせることになりますが、**遅い GPU でサンプリングするより速い**はずです
（比較実測を実施中）。

### MultiGPU を使わない現実的な代替（こちらを先に）

| 案 | 内容 |
|---|---|
| **`CLIPLoader.device = "cpu"`** | **Test 3 で必須と判明。**25.9 GB のエンコーダは 12GB カードに載らず、`device=default` だと cuda:1 で OOM する |
| **フェーズ分離の徹底** | VLM → アンロード → TextEnc → サンプリング。Phase 1 で実装済み（プロンプトを unload/purge 経由で流す） |
| **VLM の `vram_limit` を絞る** | 既定 `-1` は llama.cpp が2枚とも占有する。`6` で GPU1 使用量が 11.2GB → 2.0GB に |
| **より小さいテキストエンコーダ** | GGUF Q4_K_M（約19GB）や nvfp4（15.7GB、Ada 動作未検証）。CPU 実行が遅すぎる場合の選択肢 |
| **モニタを 3060 に挿す** | デスクトップ描画分（約1.4GB）が 4070 Ti から外れる。12GB 環境では効く |

> **制約：** `ComfyUI-llama-cpp` の `llama_cpp_model_loader` には
> `main_gpu` / `tensor_split` の指定口がありません（ソース確認済み）。
> VLM を 3060 に固定することはこのノードではできません。
> `vram_limit` で CPU 実行比率を上げるか、Phase 1 のように使用後すぐアンロードする運用になります。

**小ワザ：** モニタを 3060 側に挿すと、デスクトップ描画分（500MB〜1GB）が
4070 Ti から外れます。12GB 環境ではこれが効きます。

## 8. 独立アプリ化に向けて

将来 ComfyUI の外から叩く場合の足がかり。

- `build/build_phase1.py` はグラフを**プログラムで生成**しているので、
  パラメータ（解像度・尺・参照枚数・モード）を引数化すれば
  「設定 → ワークフロー JSON 生成 → `/api/prompt` に POST」という流れがそのまま作れます
- `build/validate.py` をそのまま CI 的なチェックに使えます
- ComfyUI の `/object_info` を起動時に取得してスキーマ検証する仕組みが既にあるため、
  カスタムノードの更新でノード仕様が変わっても検出できます
